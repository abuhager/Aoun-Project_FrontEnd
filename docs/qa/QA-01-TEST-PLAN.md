# عون — QA 01: Test Baseline & Smoke Testing

## هدف المرحلة

هذه أول مرحلة QA بعد إكمال الـ16 Flow والتنظيف. هدفها بناء خط أساس ثابت نعرف من خلاله أن النسخة قابلة للاختبار، ثم تنفيذ Smoke Test يدوي على أهم الوظائف قبل الدخول في اختبارات أعمق.

QA 01 لا تحاول إثبات أن كل تفصيل في عون خالٍ من الأخطاء. هي تجيب عن سؤال أبسط:

> هل أهم أجزاء النظام تعمل بما يكفي حتى نبدأ دورة اختبار منظمة؟

## المفاهيم التي نطبقها

| المصطلح | معناه في عون |
| --- | --- |
| Test Scenario | هدف واسع مثل: اختبار قبول عرض تبرع. |
| Test Case | خطوات محددة ومدخلات ونتيجة متوقعة لاختبار جزء من السيناريو. |
| Happy Path | المستخدم ينفذ العملية الصحيحة ببيانات صحيحة. |
| Negative Test | المستخدم يرسل بيانات خاطئة أو يحاول إجراء غير مسموح. |
| Edge Case | حالة حدية مثل عرضين لنفس الطلب أو الرجوع بعد تسجيل الخروج. |
| Smoke Test | فحص سريع لأهم الوظائف لتحديد إن كانت النسخة صالحة لاختبار أوسع. |
| Regression Test | إعادة فحص مشكلة قديمة للتأكد أنها لم تعد؛ مثل وصول المتبرع المرفوض إلى الغرض المقبول. |

## النطاق

داخل QA 01:

- تشغيل Backend وFrontend والتحقق من Health endpoints.
- فحوص الكود الحالية وProduction build.
- الصفحات العامة والمصادقة وتسجيل الخروج.
- حماية المسارات والأدوار.
- المسار الحرج: إنشاء طلب، عرضان، قبول عرض واحد، ورفض الآخر.
- خصوصية صاحب العرض المرفوض والغرض المرتبط بالطلب.
- فحص سريع للمحادثة والإشعارات وواجهة الهاتف.

خارج QA 01:

- Load وPerformance testing.
- فحص OWASP الأمني الكامل.
- اختبار كل Endpoint يدويًا.
- E2E automation وCI/CD.
- اختبارات الاستعادة والنسخ الاحتياطي والفشل المتعمد للخدمات الخارجية.

هذه البنود ستأتي في المراحل اللاحقة.

## بيئة الاختبار

نفّذ الحالات أولًا محليًا، ثم أعد Smoke subset على النسخة المرفوعة.

سجّل قبل البدء:

- Frontend commit SHA.
- Backend commit SHA.
- المتصفح وإصداره.
- نظام التشغيل.
- هل الاختبار Local أم Hosted.
- عنوان Frontend وBackend المستخدمين.
- اسم قاعدة بيانات الاختبار، من دون كتابة URI أو أسرار.

لا تنفذ الحالات التي تغيّر البيانات على قاعدة تحتوي مستخدمين حقيقيين.

## بيانات الاختبار المطلوبة

استخدم حسابات مخصصة للاختبار فقط:

| الرمز | الدور | الاستخدام |
| --- | --- | --- |
| U1 | طالب/مستفيد | إنشاء طلب وقبول العرض. |
| U2 | متبرع A | تقديم العرض الذي سيُقبل. |
| U3 | متبرع B | تقديم العرض الذي سيُرفض. |
| U4 | Admin | فحص صلاحيات الإدارة. |

لا تكتب كلمات المرور أو Tokens داخل ملفات QA أو Screenshots أو GitHub.

## شروط الدخول

يبدأ الاختبار اليدوي عندما تتحقق الشروط التالية:

- Backend `npm run verify` ناجح: Syntax و`131/131` اختبارًا.
- Frontend `npm run verify` ناجح: ESLint وTypeScript و`103/103` اختبارات.
- Frontend `npm run build` ناجح.
- `/health/live` يعيد HTTP 200.
- `/health/ready` يعيد HTTP 200 وقاعدة البيانات `connected`.
- الحسابات الأربعة متاحة ولا تحتوي بيانات حقيقية.

## طريقة التنفيذ

1. افتح [QA-01-EXECUTION-RESULTS.md](QA-01-EXECUTION-RESULTS.md) وسجّل معلومات البيئة.
2. نفّذ الحالات بالترتيب الموجود في [QA-01-TEST-CASES.md](QA-01-TEST-CASES.md).
3. لكل حالة اختر: `PASS` أو `FAIL` أو `BLOCKED`.
4. اكتب Actual Result حتى لو نجحت الحالة بجملة قصيرة.
5. عند الفشل، أنشئ تقريرًا من [QA-01-BUG-REPORT-TEMPLATE.md](QA-01-BUG-REPORT-TEMPLATE.md).
6. أصلح أخطاء `Critical` و`High` ثم أعد الحالة الفاشلة والحالات المرتبطة بها كـRegression.

## Severity وPriority

| Severity | الاستخدام |
| --- | --- |
| Critical | تسريب بيانات، دخول غير مصرح، فساد بيانات، أو توقف المسار الأساسي بالكامل. |
| High | وظيفة أساسية لا تعمل ولا يوجد بديل عملي. |
| Medium | خلل واضح مع وجود طريقة بديلة أو أثر محدود. |
| Low | نص أو تنسيق أو مشكلة بسيطة لا تمنع الاستخدام. |

Severity تصف أثر المشكلة. Priority تصف سرعة إصلاحها. قد تكون مشكلة Low severity لكنها High priority إذا كانت ظاهرة في العرض أمام مؤسسة.

## شروط الخروج

تُعتبر QA 01 مكتملة عندما:

- كل حالات Smoke نُفذت وسُجلت نتيجتها.
- لا توجد حالات `BLOCKED` بلا سبب وخطوة متابعة.
- لا توجد Bugs مفتوحة بدرجة `Critical` أو `High`.
- حالات `PRIV-001` و`ITEM-001` و`CHAT-001` ناجحة.
- نتيجة الاختبارات الآلية وProduction build ناجحة بعد آخر إصلاح.
- أُعيد اختبار أي حالة تأثرت بإصلاح Bug.

بعد ذلك نبدأ QA 02: توسيع الـManual Regression Matrix إلى بقية التدفقات والحالات السلبية والحدية.
