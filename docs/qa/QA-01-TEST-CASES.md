# عون — QA 01 Test Cases

استخدم حسابات الاختبار U1 وU2 وU3 وU4 المعرفة في خطة الاختبار، ونفّذ الحالات بالترتيب.

## Baseline

### QA01-SMK-001 — الفحوص الآلية

- النوع: Smoke / Automated baseline
- الخطوات:
  1. داخل Backend شغّل `npm ci` ثم `npm run verify`.
  2. داخل Frontend شغّل `npm ci` ثم `npm run verify`.
  3. داخل Frontend شغّل `npm run build` مع Environment صحيح.
- المتوقع:
  - Backend: `131/131` ناجحة وفحص `125` ملف JavaScript.
  - Frontend: `103/103` ناجحة وESLint وTypeScript ناجحان.
  - Production build ناجح.

### QA01-SMK-002 — Liveness

- النوع: Smoke / Happy path
- الشرط: Backend يعمل.
- الخطوات: افتح `http://localhost:5000/health/live`.
- المتوقع: HTTP 200، و`status` تساوي `ok`، ويوجد `uptime` و`timestamp`.

### QA01-SMK-003 — Readiness

- النوع: Smoke / Integration
- الشرط: Backend متصل بقاعدة بيانات الاختبار.
- الخطوات: افتح `http://localhost:5000/health/ready`.
- المتوقع: HTTP 200، و`status` تساوي `ok`، و`database` تساوي `connected`.

### QA01-SMK-004 — إقلاع Frontend

- النوع: Smoke / Happy path
- الخطوات:
  1. شغّل Frontend.
  2. افتح الصفحة الرئيسية.
  3. افتح Console وNetwork في DevTools.
- المتوقع: الصفحة تظهر، لا توجد شاشة بيضاء، ولا توجد أخطاء JavaScript غير معالجة أو طلبات أساسية 5xx.

## Public and authentication

### QA01-PUB-001 — التصفح كزائر

- النوع: Happy path
- الخطوات:
  1. افتح نافذة خاصة من دون Session.
  2. افتح `/browse` ثم تفاصيل غرض متاح.
  3. افتح `/donation-requests` ثم طلبًا عامًا.
- المتوقع: البيانات العامة فقط تظهر، ولا تظهر معلومات أو إجراءات خاصة بالمستخدمين.

### QA01-AUTH-001 — إخفاء Demo

- النوع: Configuration / Negative
- الشرط: `DEMO_LOGIN_ENABLED=false` ثم إعادة تشغيل Frontend.
- الخطوات: افتح `/login`.
- المتوقع: لا تظهر بطاقات الحسابات التجريبية، ونموذج الدخول العادي يعمل.

### QA01-AUTH-002 — إظهار Demo

- النوع: Configuration / Happy path
- الشرط: `DEMO_LOGIN_ENABLED=true` وإعداد حساب Demo كامل واحد على الأقل ثم إعادة تشغيل Frontend.
- الخطوات:
  1. افتح `/login`.
  2. اضغط بطاقة حساب Demo.
- المتوقع: تظهر البطاقات للأدوار المضبوطة فقط، ويُملأ البريد وكلمة المرور للحساب المختار.

### QA01-AUTH-003 — دخول صحيح

- النوع: Happy path
- الخطوات: ادخل باستخدام U1 ببيانات صحيحة.
- المتوقع: نجاح الدخول، ظهور هوية U1، والانتقال لوجهة داخلية آمنة.

### QA01-AUTH-004 — دخول خاطئ

- النوع: Negative
- الخطوات: استخدم بريد U1 مع كلمة مرور خاطئة.
- المتوقع: رفض الدخول برسالة مفهومة، عدم إنشاء Session، وعدم عرض Stack trace أو تفاصيل داخلية.

### QA01-AUTH-005 — تسجيل الخروج والرجوع

- النوع: Regression / Edge
- الخطوات:
  1. ادخل بحساب U1 وافتح `/dashboard`.
  2. سجل الخروج.
  3. اضغط Back ثم اعمل Refresh.
- المتوقع: لا تعود بيانات U1، ويُمنع فتح الصفحة المحمية.

### QA01-ACCESS-001 — زائر يفتح صفحة محمية

- النوع: Authorization / Negative
- الخطوات: من نافذة خاصة افتح `/dashboard` مباشرة.
- المتوقع: التحويل إلى `/login` مع Redirect داخلي آمن، وعدم ظهور محتوى Dashboard للحظة قابلة للاستخدام.

### QA01-ACCESS-002 — مستخدم عادي يفتح الإدارة

- النوع: Authorization / Negative
- الخطوات: ادخل بحساب U1 ثم افتح `/admin` مباشرة.
- المتوقع: منع الوصول دون تسريب بيانات الإدارة. لا يكفي إخفاء رابط الإدارة من Navbar.

## Critical donation-request regression

نفّذ الحالات التالية كسلسلة واحدة وسجل IDs الخاصة بالطلب والعروض محليًا في ورقة النتائج فقط.

### QA01-REQ-001 — إنشاء طلب

- النوع: Happy path
- الخطوات:
  1. ادخل بحساب U1.
  2. أنشئ طلب تبرع ببيانات وصورة/تفاصيل صالحة حسب النموذج.
  3. افتح تفاصيل الطلب بعد الإنشاء.
- المتوقع: إنشاء الطلب مرة واحدة، ظهوره بالحالة الصحيحة، وعدم إنشاء نسخة ثانية عند الضغط المتكرر.

### QA01-OFFER-001 — العرض الأول

- النوع: Happy path
- الخطوات:
  1. ادخل بحساب U2.
  2. افتح طلب U1.
  3. قدم عرضًا صالحًا.
- المتوقع: إنشاء عرض Pending مرتبط بـU2 والطلب، وعدم فتح `offerId` كأنه Item ID.

### QA01-OFFER-002 — العرض الثاني

- النوع: Edge case
- الخطوات: ادخل بحساب U3 وقدم عرضًا ثانيًا صالحًا للطلب نفسه.
- المتوقع: وجود عرض Pending مستقل لـU3 من دون تغيير عرض U2.

### QA01-MATCH-001 — قبول عرض واحد

- النوع: Happy path / Data integrity
- الخطوات:
  1. ادخل بحساب U1.
  2. افتح عروض الطلب.
  3. اقبل عرض U2 مرة واحدة.
  4. اعمل Refresh وافتح الطلب من نافذة أخرى.
- المتوقع:
  - عرض U2 يصبح Accepted.
  - عرض U3 يصبح Rejected/Expired حسب عقد النظام.
  - الطلب ينتقل للحالة النهائية الصحيحة.
  - يُنشأ غرض مرتبط واحد فقط ومحجوز للطرفين.

### QA01-PRIV-001 — عزل صاحب العرض المرفوض

- النوع: Critical regression / Authorization
- الخطوات:
  1. ادخل بحساب U3 صاحب العرض المرفوض.
  2. افتح إشعار الرفض.
  3. غيّر IDs يدويًا في الروابط أو الطلبات لمحاولة فتح الغرض المقبول.
- المتوقع:
  - الإشعار يفتح الطلب أو وجهة آمنة فقط.
  - لا يظهر رابط أو صورة أو تفاصيل الغرض الفائز الخاصة.
  - محاولة فتح الغرض المرتبط مباشرة تُرفض بـ403 أو 404 مناسب، ولا تعيد بيانات حساسة.

### QA01-ITEM-001 — الغرض المقبول ليس عامًا

- النوع: Critical regression / Privacy
- الخطوات:
  1. افتح `/browse` كزائر، ثم بحساب U3.
  2. ابحث عن الغرض الذي نتج عن قبول عرض U2.
  3. جرب فتح رابطه المباشر إن كان ID معروفًا.
- المتوقع: الغرض لا يظهر في التصفح العام ولا يُفتح إلا للطرفين الفعليين أو الإدارة.

### QA01-CHAT-001 — أطراف المحادثة

- النوع: Authorization / Integration
- الخطوات:
  1. افتح المحادثة من U1 ثم U2 وأرسل رسالة اختبار.
  2. افتح نفس `conversationId` أو رابط المحادثة بحساب U3.
- المتوقع: U1 وU2 فقط يستطيعان القراءة والإرسال، وU3 يُمنع حتى لو عرف المعرّف.

## UI smoke

### QA01-UI-001 — شاشة هاتف 320px

- النوع: UI / Accessibility smoke
- الخطوات:
  1. استخدم Responsive Mode بعرض 320px.
  2. افحص الصفحة الرئيسية، Login، Browse، Dashboard، الإشعارات، وصفحة الطلب.
  3. افتح القوائم والحوارات واستخدم Tab وEscape.
- المتوقع: لا يوجد تمرير أفقي غير مقصود، الأزرار قابلة للضغط، Navbar والإشعارات ظاهرة، والحوار يغلق بـEscape ويعيد التركيز.
